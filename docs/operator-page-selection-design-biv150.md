# 页选择稀疏 decode attention：可行性设计与前置闸门

本文是算子线的下一阶段设计，不占设备、不含新测量；所有数字来自已登记的原件或公开论文，推断处单独标注。目标是判断"在 6 小时内拿到 +20% 吞吐"是否成立，以及需要哪些前置闸门。

## 1. 现状基线（本机实测）

- decode attention 在正确段数下已达到 **512 GB/s（b64/kv4096, seg2: 0.5242 ms/层）** 与 **510 GB/s（b16/kv16384, seg8: 0.5264 ms/层）**，即 553 GB/s 锚点的 92–93%。同一批测试里 seg16 只有 415 GB/s——之前引用的 415 是"服务常量 16 段"的数字，不是最优配置。
- 因此 bf16 路径的地板就是 26 ms/step（14.4 GB ÷ 553 GB/s），当前 27.5 ms，**剩余 ≤7%**。
- `evict_first` 提示：415.2 vs 414.9 GB/s，无差别（KV 每字节只读一次）。
- 循环流水线（`tl.range(num_stages)`）：比 `while` 慢 21–35%，已回滚。
- 固定 Δ 的单遍 V-skip：Δ 从 6 到 14 都没有页被跳过（随机数据下页分数平坦），且分支本身慢 3–6%。

结论：要再拿 20%，**必须少读页**，没有别的路。

## 2. 方案比较（来自公开工作，数字为论文自述）

| 方案 | 机制 | 额外状态 | 论文收益 | 与我校验过的约束的冲突 |
|---|---|---|---|---|
| **Quest**（2406.10774） | 每页存每通道 K 的 min/max，用 $s=\sum_d \max(q_d \max_d, q_d \min_d)$ 估计页上界，只算 top-k 页 | 512 B/页/头 ≈ KV 的 6.25% | 32K 上下文 self-attn 7.03×、端到端 1.74×；预算 1/6–1/10 时 LongBench 无损 | 需要页统计（写路径或一次性扫描）；本机 KV 21 GB/32 GiB，6% 的旁路缓冲约 1.3 GB，可接受 |
| **LServe**（2502.14866, MLSys25） | 块稀疏统一框架；**页选择结果可跨步复用**；一半头转 streaming | 页表缓存 | 相对 vLLM decode 1.3–2.1× | 头分类要在本模型上重测；GQA 组内分头会破坏 ROWS=8 的共享页表 |
| **SnapKV**（2404.14469） | prefill 末用观察窗 Q 一次性投票选位置 | 每头索引集 | 压缩 92%，生成 3.6× | 一次性决策无法随 CoT 调整 |
| **H2O**（2306.14048） | 累计注意力分数的 heavy hitter + recent | 4 B/token/头 + 物理搬移 | 20% 预算多数任务持平 | 与分页共享块冲突，要改写 KV 搬移 |
| **StreamingLLM**（2309.17453） | 4 sink + 最近窗口 | 无 | 4M token | 精度原则上不可接受，但**是最好的敏感度探针** |
| Loki / RetrievalAttention / ShadowKV / RocketKV | 低秩/索引/offload 类 | 数百 MB–数 GB | 3–5× | 都要求改 KV 存储或走 CPU/PCIe，32 GiB 单卡不成立 |

（推断）按"端到端增益 × 过精度门概率"排序：Quest 式页选择 > 其上叠加 LServe 的跨步复用 > SnapKV 式一次性掩码。H2O 与低秩/检索类不建议。

## 3. 推荐形态：上一步页分数 + 边缘页强制保留

为避免引入 1.3 GB 的 min/max 旁路缓冲与一次性扫描，先做 Quest 的"时间复用"简化版：

- 每层维护一个 `[max_seqs, kv_heads, max_pages]` fp32 分数平面。以 `k_cache.data_ptr()` 为键在 wrapper 里缓存，天然区分层；64 序列 × 2 头 × 320 页 × 4 B ≈ 164 KB/层，42 层约 7 MB。
- 每个 decode 步：kernel 在读到某页时把该页的 `page_max` 写回平面；下一步读回同页分数，若低于**本段最佳页**超过 Δ（log2 单位）就整页跳过 K 与 V（不只 V），并跳过该项对分母的贡献；首 2 页与末 2 页强制保留；序列首步（无历史分数）稠密跑一次。
- 预期收益（按 §1 的 27.5 ms 与 60.35 ms TPOT）：f=0.5 → 13.8 ms → TPOT 46.6 → **+29%**；f=0.35 → 9.6 ms → **+39%**；f=0.7 → 19.3 ms → **+16%**。每步额外开销是分数平面读（几十 KB）与每个 program 对段内页的一次扫描（≤320 次标量读），估 0.5–1 ms。

## 4. 必须前置回答的问题（精度闸门）

1. **本 workload 的页分数是否集中？** 只有集中才既有得跳、又不掉精度。随机 K/Q 的微测（Δ=14 无一页被跳）说明不了模型真实分布，必须在服务上量。
2. **MATH Level-3 对"缺页"有多敏感？** 最便宜的探针：解码时只保留"首 32 token + 最近 W token"（纯窗口，无选择），跑一次官方 Level-3。若仍 ≥0.965，说明该基准对中段上下文不敏感、页选择大概率能过；若 <0.95，放弃所有稀疏方案。这一步约 25 分钟，是整条线的 go/no-go。
3. **序列槽复用**：vLLM 会把同一槽位给新请求，旧分数会误导首步；需要"首步稠密 + 首步重写全部分数"，并评估每次新序列的一个坏 token 是否影响精度。

## 5. 集成点与代价（代码层）

- `vllm_fl/patches/biv150_gqa_decode.py`：kernel 增加 `score_ptr / SKIP_ENABLED / SKIP_DELTA` 三个参数与"读上一步分数→跳过整页"的分支；wrapper 里按 `k_cache.data_ptr()` 惰性分配分数平面，并在 `_pick_segments` 之外不改任何既有门控。
- 该 kernel 在 attention 自定义算子外层被调用，**不进入 torch.compile 图内**，因此不受此前 int8 那七种编译墙限制（这是它与线性层方案的关键差别）。
- 回滚方式：`VLLM_FL_BIV150_GQA_SKIP=0`（默认）时与当前交付版逐位一致。

## 6. 结论

- 页选择是目前唯一可能达到 +20% 的算子路线，量级足够（f=0.5 即 +29%），且集成成本低于 int8 线（不进编译图、不改写 KV 路径、内存 <10 MB）。
- 成败**完全取决于 Level-3**：建议先花 25 分钟跑"窗口探针"回答基准敏感度，再决定是否投入选择逻辑（约 2 小时）。没有这一步就上，风险不可控。

（本文不含新设备测量；设备当前由另一 agent 使用。）
